# Beauty SaaS 統一營運系統設計規格（待審閱）

狀態：設計審閱稿；本文件不授權正式資料遷移、LINE 設定、薪資計算上線或部署。

## 1. 目標與系統邊界

保留現有 beauty-saas 的店主桌面後台。店家 LINE OA 的 rich menu／分享連結開啟手機網頁，顧客自行預約，美容師以 LINE 登入查自己的班表與服務，櫃台在桌面或手機代訂電話、私人 LINE 與現場客人。所有入口呼叫同一組舊系統預約服務，寫入現有 PostgreSQL `public.bookings`、`booking_segments`、`booking_staff_allocations`、`booking_resource_allocations`、客戶及通知 outbox。一次交易決定預約、員工與資源配置；通知失敗不得撤銷已成立預約。不同店家及分店資料隔離。

現有候選版 `/line-booking/*` 與 `line_booking` schema 是可用的手機 UX／身分驗證原型，但仍形成第二個預約資料核心。正式方向是保留 UI 及必要的 LINE adapter，改接舊 `src/server/public-booking`、`src/server/availability`、`src/server/booking`、`src/server/merchant`；完成切換前不得同時開放兩套預約寫入同一店。候選 dry-run 舊資料轉新 schema 工具只作盤點，不是此方向的正式遷移器。

## 2. 現有能力與缺口

| 領域 | 現有程式／資料 | 需要補足 |
| --- | --- | --- |
| 店主桌面 | `src/app/merchant/[view]`、`MerchantWorkspace` 有日曆、預約、顧客、服務、人員、資源、報表及設定 | 與 LINE 手機端共用舊預約核心；權限及模組開關涵蓋選單、頁面和 API |
| 員工與服務資格 | `staff_profiles`、`service_staff_assignments`、`staff_service_assignments`、排班與請假表；`SERVICE_PROVIDER` 已有 own booking 權限 | 櫃台可管理每人能做的服務、有效期與停用；明確選人／不指定與輪序派工 |
| 預約與資源 | 舊系統有 segment、staff/resource allocation、緩衝、hold、取消政策 | 線上及現場共用原子派工交易，不能只在 UI 過濾可用人員 |
| 顧客 | `customers` 有生日、黑名單，CRM 有標籤與備註，公開預約已有黑名單檢查 | VIP 規則、黑名單覆核及有效期、生日優惠資格與同意紀錄 |
| 會員錢包與電子券 | 現有預約付款、退款資料及 `MEMBERSHIPS_PACKAGES` entitlement；未找到已可用的儲值錢包／電子券帳本 | 有償儲值、贈送額度、折扣券及服務套票分帳；核銷、退款、對帳與發券權限 |
| 通知 | 舊 `notification_outbox`、LINE webhook／adapter | 每店 OA 渠道設定、身分／客戶連結、重試及去重；現有環境變數是單組 LINE 渠道 |
| 出勤與薪資 | 有人員排班、請假及預約服務狀態 | 未找到出勤打卡、薪資或抽成帳本模組；需要新資料結構與審核流程 |
| 可選模組 | `plan_entitlements`、`organization_feature_overrides`、`getEntitlement` | 依方案及店家設定顯示適用功能；目前 merchant 導覽大多固定列出 |

服務不是按摩專用：沿用 `services`、`service_variants`、`service_categories`、`location_services` 與服務所需資源類型。店家可停用不適用的業務模組；人員服務資格、資源需求及預約政策仍由該分店設定。

## 3. 身分、裝置與角色

每位員工有一個內部 `staff_profile_id`，角色來自已啟用的 `organization_memberships`／`location_memberships`，不是來自 LINE 暱稱、電話、手機裝置或 URL。LINE 登入後伺服器驗證 token、channel、provider 與期限，以 `(provider_id, line_user_id)` 找到經核准的連結，再解析該店角色與可操作分店。店主同時是美容師時，可有兩種能力；手機預設顯示其工作角色並可明確切換，敏感操作仍逐項查 capability。顧客會員連到既有 `customers`；同一人可以同時是員工與顧客，但兩種關係獨立。

**同一 LINE 帳號在多部支援的裝置登入**：映射到同一內部員工，裝置各有可撤銷的短期 session；登出某裝置、全裝置撤銷、停職或移除 membership 應使相應 session 失效。避免把裝置 ID 當權限。不能保證任意兩部手機能同時登入同一 LINE 帳號；[LINE 支援中心](https://help-o.line.me/line/smartphone?contentId=20000132&lang=zh-Hant) 指出 iPhone 不能作追加裝置、Android 可作主要或追加裝置。因此產品要支援「不同 LINE 帳號連到同一員工」的情況：先驗證兩個帳號各自的 LINE 身分，再由有權限的店主／管理員核准連結，記錄申請、核准人、時間及撤銷歷史；不能靠姓名、電話或同一手機自動合併。若 LINE Login 與 OA 位於不同 provider，兩個 userId 不能視作同一人，必須走明確連結流程。每店 OA/channel 配置及 callback 要映射到正確組織與分店，憑證僅在伺服器保存。舊 `customer_contact_links` 可保留顧客連絡方式，但須核對 provider 範圍與唯一鍵，不能直接用原字串推定身分。解除連結或員工離職後，撤銷對應 session；歷史出勤和薪資仍保持原內部員工 ID，不因 LINE 帳號變動重新歸屬。

顧客可見自己的預約與會員優惠；美容師可見自己的客戶聯絡資訊及別人的忙碌狀態；櫃台／店主依分店授權可安排所有人員。薪資、黑名單原因和完整客戶備註有單獨能力限制。所有手動覆寫與身分連結均寫 audit。

## 4. 服務資格與統一派工

櫃台管理員或店主在現有桌面後台設定「美容師 × 分店 × 服務變體」資格，至少有啟用狀態、有效起訖、可線上指定、可現場派工、資格版本／修改紀錄；可選技能等級或證照限制須另行設定。預約建立與改期時，伺服器以當時有效資格再次驗證。停用資格不回寫歷史服務；未來已指派預約進入待處理清單，由櫃台人工改派或通知，不可靜默取消。

指定美容師：依服務資格、排班、休息／請假、未來既有預約、服務時長及前後緩衝、床位／房間／設備可用性求交集，建立時鎖定預約與分配。**不指定美容師、現場臨時客、櫃台代訂**：以相同候選過濾，依店家輪序策略挑人；不指定的線上預約應在預約當下即指派可服務的人員與資源，除非店家明確採「到店才指派」政策，且須保證容量。預約狀態及服務來源分開記錄，現場客也須有顧客紀錄或明確的匿名訪客政策。

輪序預設以「分店 × 當日／班次 × 服務資格群」為範圍，按該班次**已成功確認的即時派工次數**最少、上次即時受派時間最早、穩定員工 ID 決勝；計數只在**立即到店並確認服務的交易成功**時增加。未來線上預約即使已指派美容師也不增加即時輪序計數，但立即保留該時段員工及資源容量。候選人須已到班、未休息、無重疊工作及即將到來的預約衝突，且資源足夠。略過須記原因（休息、請假、技能不足、忙碌、拒接等）；休息結束或員工重新可接案後，回到下一次正常候選。開始服務前取消且未占用實際服務者，預設以補償事件回補該次計數；服務開始後取消或未到不自動倒轉，改由櫃台依政策覆核。櫃台覆寫須指定理由並留 audit；同時兩個櫃台派工由資料庫交易鎖／排除約束避免重複指派。任何失敗都不應創造「已預約但無人或無床」的紀錄。

## 5. 會員、黑名單、VIP、生日優惠

沿用現有顧客表與 CRM 標籤；VIP 是組織內明確的會員等級／標記，有設定者、有效期、可見範圍與優惠規則，不由單一員工私下口頭標記。黑名單預設只限制該店或組織的**新預約**，原因與證據限授權管理者看；一般美容師只看到可否接受新預約的必要結果，不看到原因、內部備註或其他店家的紀錄。有到期／定期覆核、解除與申訴處理，既有預約由櫃台審核，不能無通知自動取消。是否跨分店共用黑名單由店家明確設定；不做跨商家共享黑名單。

生日資料最小化使用，優惠資格可只以月／日計算；設定優惠有效窗、每年／每人使用次數、能否與 VIP／套票同用、退訂或取消時的回補規則。優惠核銷與預約／付款交易關聯並防重複。生日推播與優惠通知須有可追溯的行銷同意及退訂狀態；同意預約通知不等於同意行銷。未設定渠道或未同意時，只在會員頁展示資格，不自動付費發送訊息。

### 5A. 會員錢包、電子券與節慶活動

「儲值 10,000 元贈 1,000 元」須拆成不同權益：**有償儲值本金 10,000** 與 **商家促銷贈送額度 1,000**。折扣券、固定金額抵用券、服務次數套票各有自己的規則及帳本，不與儲值金額混成單一餘額。會員在 LINE 手機頁可看各類可用、已保留、已使用及調整紀錄；店主桌面可看發行、使用與負債對帳。所有增加、保留、釋放、核銷、退款、作廢都採不可變事件並附原交易 ID、分店、操作者與規則版本；餘額為事件衍生值，不直接手改。預約時保留、實際結帳時核銷，取消或逾時釋放，重試不得重複扣款。

電子券出示採短效、單一會員、單店／可用分店範圍的一次性 QR 或核銷碼；店員掃碼後由伺服器再查會員、券狀態、服務、有效窗與重複核銷，手機截圖不是權利證明。預設不支援離線最終核銷；斷線時只能記待查申請，恢復連線後由伺服器確認，不可先當作付款成功。會員轉讓、跨店使用、部分使用、逾期與退款規則應依券種明示並保存發行時條款快照。有償儲值及優惠券的有效期、退費、移轉與法律性質不可套用同一政策；正式商品條款與台灣相關法規須另行審查，不預設本金可以到期沒收。[經濟部商品（服務）禮券規範](https://law.moea.gov.tw/LawContent.aspx?id=GL000996)對適用的有償禮券要求揭露履約保障及退還程序，並禁止載明使用期限；無償發行的抵用／折扣券不在該規範的同一定義內，但「儲值贈送額度」不能只憑名稱就認定可任意到期或不退。不同美容服務還應核對[美容契約規範](https://www.ey.gov.tw/File/3F8982FEDAE7E152?A=C)及適用時的[瘦身美容規範](https://www.ey.gov.tw/File/853FDC20BF628E1C?A=C)。

預設示例（僅供產品設計，非會計或法律規則）：會員付 10,000 元獲得 10,000 本金及 1,000 贈送額度；若購買 1,000 元服務，建議預設先依明示的**本金優先**政策扣本金 1,000，付款拆分記為「本金 1,000、贈送 0」，剩餘本金 9,000、贈送 1,000。若店家選擇比例扣抵，交易應清楚列出兩種來源及結果（例如按 10:1 分攤時，若以新台幣整元記帳，固定捨入後本金 909、贈送 91；細分貨幣單位與尾差規則須由付款幣別決定）。同一店不可在結帳後才臨時改扣抵順序；退款應追溯原付款來源比例或優先順序，回補本金／贈送額度或形成待人工審核差額，已失效贈送額度的處理需依發行時條款決定。不得把「儲值入金」和「以儲值額度支付服務」兩次都算成服務業績或美容師抽成。

節慶活動例如「母親節帶媽媽同行八折」設為活動規則：可用日期、服務／分店、對象條件、每會員或每交易次數、折扣上限、是否與生日、VIP、套票、贈送額度併用及衝突優先序。顧客結帳前顯示原價、各優惠及實付金額；不為驗證同行關係而收集母親身分證件或建立家庭關係圖，預設由櫃台以最小的「符合活動條件」人工確認並留稽核。活動折扣屬顧客利益，其資格判定與員工抽成基礎分開計算。

## 6. 出勤與薪資

沿用既有排班、請假與預約服務事實，新建不可變的上下班／休息打卡事件。每筆記錄員工、分店、時間、來源與更正鏈；錯誤打卡以更正申請與核准事件處理，不直接覆寫原事件。主管可核對排班、遲到、缺勤、加班、跨日班與跨店工作；地點／裝置證據僅在必要且經告知時收集。LINE 登入不等於打卡，預約完成也不等於出勤。若適用台灣勞動法，出勤紀錄須記錄實際時間至分鐘並依規定保存、可供員工查閱／取得副本；系統設計預留至少五年保存期，實際適用範圍與保存規則於上線前依法確認。加班即使尚待核准，也保留實際工時與覆核結果，不刪除原始打卡。

薪資規則須有生效日期與版本：基本薪資／時薪、服務別或員工別抽成、指定／輪序派工、銷售或套票分攤、退款／取消／未到的回沖、加班與請假項目。從實際打卡、已完成服務及已核准的更正產生可重算的試算明細；尚待核准的異常時間保留於試算並標記待覆核，不可直接捨棄。再經獨立薪資權限的主管審核與鎖期，形成不可變薪資帳本／薪資單；後續差異以調整項記錄，不能改寫過往已核准薪資。一般櫃台、其他美容師及店家顧客不得讀取薪資資料；員工只能看自己的薪資單。薪資單逐項顯示約定工資、各加給與扣除、實發數額及計算來源，提供員工可下載／列印版本；適用台灣法時，薪資清冊保存期預留至少五年。加班費依適用期間的法令、契約、休息日類型與規則版本計算，不固定套用單一倍率或一律「月薪÷240」。抽成名稱也不自動決定員工是否適用勞動法。顧客付款、平台帳單及員工薪資為不同帳；此階段不執行銀行匯款，也不宣稱符合任何地區勞動／稅務法規，正式計薪規則需由店家與當地專業人士確認。LINE 只可發「薪資單可查看」等一般通知，不在訊息中放金額或明細。

員工抽成規則引擎需按分店、服務類型、員工、付款組件及生效日期版本設定，允許固定每筆金額或比例；明確選擇計算基礎是原價、折扣後服務淨價、實收款，或分攤後的服務收入，並規定優先序及上限。現金、一般刷卡、有償儲值本金、贈送額度、折扣券、套票可有不同抽成率，**顧客折扣或贈送額度的使用不自動等於員工少拿薪資**；由店家已公告的員工契約與規則決定。若一筆服務由多名美容師執行，記錄可稽核的分攤比例或固定分額，總額不能重複發放。付款手續費及稅額是否進入抽成基礎須明訂；退款、改期、取消與套票退費以原服務與付款組件產生反向抽成事件，已結薪資不得改寫，只能下期調整並可追溯。

規則編輯器須讓管理員明確選擇百分比基礎（原價、折扣後淨價、或排除贈送額度後的實付服務部分），或固定金額的計算單位（每筆訂單、每項服務、每次實際核銷），顯示優先序、可否疊加與發行後預覽；互相衝突、同一服務重複付抽成的規則不得發布。示例僅用於介面預覽：標價 1,000、節慶八折後 800，40% 原價抽成為 400、40% 淨價抽成為 320；若 800 由本金 600 與贈送額度 200 支付，且店家選「只計本金來源 40%」，則為 240。固定每項服務 300 是另一種可選規則，預設不與上述百分比相加。儲值當下若另設儲值銷售獎金，與服務完成後抽成為不同事件及預算，預設關閉；有償儲值本金用於服務付款時仍是付款來源，不因當下沒有再收現金就被視為零營收。退款回沖須先連到原服務與抽成項，不能不經審核直接從已核准薪資扣除。

法規核對入口：[勞動基準法第 23 條](https://laws.mol.gov.tw/FLAW/FLAWDOC01.aspx?flno=23&id=FL014930)、[勞動基準法施行細則第 14-1 條](https://laws.mol.gov.tw/flaw/FLAWDOC01.aspx?flno=14-1&id=FL014931)、[勞動部加班費試算系統](https://calcr2.mol.gov.tw/Index)。本規格是資料與流程設計，非法律判定。

## 7. 可選模組與介面

既有方案 entitlement 決定組織可使用的上限，店家管理員可在上限內啟用服務模組；停用時隱藏不適用的選單與手機入口，但保留歷史資料與結算責任。伺服器頁面和 API 仍逐項驗證 entitlement、分店與角色；隱藏按鈕不是授權。核心預約、基本顧客及安全稽核不可關閉到破壞既有預約。多業態用「能力與設定」組合，不把按摩、臉部護理、美甲硬編成不同系統。

手機介面以顧客的「預約／我的預約／會員優惠」與美容師的「今日工作／可接服務／出勤」為主要入口；櫃台可快速新增現場客、選服務、看候選美容師與派工理由。以觸控目標、明確步驟、狀態反饋及無障礙為設計檢查。桌面後台保留完整配置、財務與稽核頁。

### 7A. 跨模組事件與責任邊界

同類產品的可參考做法包括 [Fresha](https://www.fresha.com/for-business/features) 的人員／資源日程、[SimplyBook.me](https://help.simplybook.me/index.php?title=Special%3AMyLanguage%2FRelated_Resources_custom_feature) 的關聯資源可用性，以及 [Booksy](https://support.booksy.com/hc/en-us/articles/16463469277714-How-does-the-waitlist-work) 的候補需求與正式預約分離。以下是**本系統設計推論**，不是聲稱三者有完全相同的流程；各模組仍在同一應用及資料庫交易邊界內，不新增微服務。

| 事件／轉換 | 必須同步處理 | 交易後事件／可重試處理 |
| --- | --- | --- |
| 查詢時段 → 保留 hold | 服務資格、員工班表與休息、未來預約、房／床／設備容量、hold 到期與門市政策 | 無行銷訊息；逾時釋放可由工作排程補償 |
| hold → 確認預約 | 原子確認員工／資源分配、顧客與政策版本、優惠券或套票**保留**；重試只得同一預約 | 預約通知 outbox；失敗重試但預約維持成立 |
| 到店 → 開始 → 完成服務 | 狀態與實際執行人員、服務項目、時長／改派紀錄；未完成不可當作已賺取抽成 | 完成事件供結帳與抽成試算；不以打卡或預約時間代替實際服務 |
| 結帳／核銷 | 原價、活動折扣、付款來源、本金／贈送、券／套票使用與稅費拆分記入不可變帳本；防重複 | 收據、會員餘額與員工抽成試算更新；通知不含敏感薪資 |
| 抽成 → 薪資試算 → 核准 | 使用當時規則版本、實際服務分攤與實收組件；打卡異常待覆核，核准後鎖期 | 給員工發不含金額的薪資單可用通知 |
| 取消／未到／改期 | 釋放未使用 hold、員工與資源，按發行條款決定券保留解除或已使用券恢復；改期須在新時段鎖成功後釋放舊時段，避免中間遺失 | 客戶及員工通知；原交易調整，已結薪資走下期補償 |
| 部分退款 | 對原服務與原付款來源逐項分攤退款，包含本金、贈送、券及套票，禁止超額退款 | 負向抽成與員工薪資調整；退款通知去重 |
| 員工請假／離職 | 查出未來已分配預約；先保留原預約及顧客權益，列待改派／待聯絡 | 通知櫃台、顧客與相關員工；撤銷員工 session，歷史服務／薪資歸屬不改 |
| 服務價格、優惠或抽成規則變更 | 新規則只適用生效後交易；既有預約及已發券保存當時價格／條款快照 | 受影響未來預約供櫃台審視，不在背景重算既有付款或薪資 |
| 停用可選模組 | 阻止新的發行或新交易，已售儲值／套票及未結預約仍可讀、兌付、退款、對帳 | 稽核、待履行義務清單；不可藉停用模組消除負債 |

跨模組事件須含店家、分店、穩定事件 ID、實體 ID、版本及發生時間；同一事件重送只處理一次，outbox 發送採至少一次交付及消費端去重。員工、服務、資源配置與 hold／確認屬資料庫原子條件；外部 LINE 或電郵失敗不得回滾已確認預約。對外通知僅放必要資料。

一筆預約若有多位服務人員，服務 segment、實際執行人員、折扣、付款及抽成均須按 segment 或明確比例分攤，總額和明細相等；不能每位員工各領整筆抽成。舊資料模型以單一 `customer_id` 作預約所有人；多人同行若要各自核銷會員權益，預設拆成彼此關聯的多筆顧客預約及各自結帳，待明確設計參與者模型後才支援一筆預約多會員付款。服務進行中臨時增加項目、換人或改套票，需櫃台確認新價格與資格、預留資源、記錄顧客同意及規則快照；已結帳項目不得直接覆寫。

本表列的是**核心一致性需求**，不是要求同一期完成全部模組。P0 必須完成唯一預約核心、原子容量與通知去重；P1 加入技能派工及改派；P2 才開放錢包、電子券及退款分帳；P3 才使用抽成與薪資鎖期。候補、行銷自動化、複雜多會員合併結帳列為後續選用能力，不能阻礙前述核心驗收。

## 8. 分階段交付與轉換

**P0：單一核心與身分。** 建立 LINE 身分到現有 profile／customer 的經核准連結、每店渠道配置、角色權限與可撤銷 session；讓手機端讀寫舊預約服務。切換前以合成資料比較手機和桌面的預約 ID、時段、資源與取消結果。先關閉或限制候選 `line_booking` 寫入；禁止雙寫。

**P1：資格與派工。** 桌面資格管理、指定／不指定預約、即時到店派工及原子輪序交易。用多櫃台併發、同資源競爭、未來預約碰撞、取消／改派／略過測試。

**P2：會員與活動。** VIP／黑名單政策、生日優惠與同意；再做有償儲值、贈送額度、電子券／套票的分帳、核銷與退款對帳。先以合成交易及通知測試，再以已核准的店家渠道試用；財務條款與法規審查完成前不啟用真實儲值。

**P3：出勤薪資。** 打卡／更正／審核、薪資規則試算、版本化帳本與薪資單；試算至少與一段人工核對期對帳後才考慮正式使用。

每階段用既有 Vercel／Supabase 專案的隔離測試環境和合成資料驗證，不另建付費服務、不改實際 OA 設定。若切換失敗，先停止手機新入口，回到既有桌面與公開預約入口；保留已成立預約與 audit 供對帳，不刪歷史資料。通知故障由 outbox 重試，不回滾預約。

## 9. 驗收情境與待決設定

- 同一員工在兩部 LINE 支援的裝置以同一帳號登入，顯示同一班表；撤銷一個 session 不影響另一個。不同帳號未核准前不能互看資料，核准與撤銷均可稽核；不假設兩部 iPhone 可同時使用同一 LINE 帳號。
- 櫃台停用美容師的某項服務後，線上與現場的新預約不再派給該人；已存在的未來預約列入待處理。兩名櫃台同時安排最後一位可用美容師／床位，只有一筆成功。
- 現場不指定、線上不指定、指定美容師預約在同一日曆互相阻擋；忙碌、休息與即將到來的預約會影響輪序候選。手動覆寫必須有理由。
- 被黑名單限制的會員不可再自助訂位；VIP 與生日優惠正確顯示資格，但未同意行銷者不會收到生日推播。跨店資料不外洩。
- 儲值 10,000 贈 1,000 必須分帳；同一核銷碼重複掃描只有一次成功，斷線不得假裝成功；本金、贈送、節慶折扣、套票與退款皆能回溯原交易。櫃台選擇母親節八折時需留條件確認，活動超期或超額不得核銷。
- 同筆 1,000 元服務以現金、本金、贈送或折扣券支付時，依有效版本得到不同但可重算的抽成明細；儲值入金不重複算抽成；多員工分攤總額不超過原定抽成，退款產生可追溯回沖。
- 出勤更正、退款與取消後，薪資試算可追溯來源和規則版本；已核准薪資只能由調整項修正。

建議預設：輪序按分店／班次／服務資格群計算；只有即時服務推進輪序；黑名單以單組織為範圍，跨分店是否共用由管理員設定；生日優惠每年每人一次且不與其他折扣疊加；不同 LINE 帳號合併需兩個帳號各自驗證加管理員核准；儲值本金與贈送額度分帳，預設本金優先且不離線核銷，活動不可疊加，員工抽成以折扣後服務淨價且依付款組件明示差異為起點。待店家確認的最小業務選擇是：不指定的**未來**預約要立即鎖定美容師，還是到店前才派工；建議立即鎖定，以保障容量。各店的實際輪序、抽成、加班、退款與優惠條款需在實作前配置確認。
